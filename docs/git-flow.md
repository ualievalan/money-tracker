## Git flow и Merge Request

Цель этого файла — чтобы любой джун мог:

- создать ветку под задачу;
- делать аккуратные коммиты;
- создать Merge Request;
- назначить ревьюера (Bekzhan);
- решить конфликты.

### Основные правила

- **Главная ветка**: `main`. В ней всегда только рабочий код.
- **Работаем только через feature‑ветки** — никогда не коммитим прямо в `main`.
- **Одна задача → одна ветка → один Merge Request.**

### Как назвать ветку

Формат:

- **feature/<кратко‑о‑задаче>**

Примеры:

- `feature/auth-error-messages`
- `feature/transactions-cache`

### Как создать ветку и запустить работу

```bash
git checkout main
git pull origin main         # обновить main

git checkout -b feature/auth-error-messages
```

Пишешь код в своей ветке, периодически коммитишь.

### Коммиты

- Коммит должен отвечать на вопрос **«что изменилось?»**.
- Язык — русский или английский, но **последовательно**.
- Не делаем коммиты вида `fix`, `wip`, `update`.

Примеры хороших сообщений:

- `feat(auth): добавить отображение ошибок Supabase`
- `refactor(home): вынести bottom nav в отдельный виджет`
- `fix(transactions): починить фильтрацию по дате`

Команда:

```bash
git add lib/features/auth/...
git commit -m "feat(auth): добавить отображение ошибок Supabase"
```

### Как отправить ветку в GitLab

```bash
git push -u origin feature/auth-error-messages
```

После первого пуша Git напишет URL для создания Merge Request — на него можно перейти.

### Как создать Merge Request и назначить ревьюера

1. Открыть проект в GitLab.
2. Перейти в **Merge requests → New merge request**.
3. **Source branch** — твоя ветка (`feature/...`), **Target branch** — `main`.
4. В заголовке MР коротко описать суть:
   - `feat(auth): обработка ошибок логина`.
5. В описании:
   - что сделал (2–5 буллетов);
   - как тестировать (шаги).
6. В поле **Assignee** поставить **себя**.
7. В поле **Reviewers** добавить **Bekzhan**.
8. Нажать **Create merge request**.

### Когда MR готов к ревью

Перед тем как звать ревьюера:

- убедись, что код компилируется;
- локально прогнал хотя бы базовый сценарий (логин, основной экран);
- CI‑пайплайн в GitLab для ветки **зелёный**.

Если MR ещё в процессе, можно повесить префикс в заголовок:

- `WIP: feat(auth): ...` — работа в процессе, ревью не нужно.

Когда готово — убери `WIP`.

### Как подтянуть изменения из main в свою ветку

Если `main` ушёл вперёд (GitLab показывает, что ветка **out of date**), нужно влить `main` в свою ветку:

```bash
git checkout main
git pull origin main          # обновляем main

git checkout feature/auth-error-messages
git merge origin/main         # вливаем main в свою ветку
```

В случае конфликтов:

1. Git покажет конфликтные файлы.
2. В IDE (Cursor / VS Code / Android Studio) открыть каждый конфликтный файл, выбрать нужные изменения.
3. После ручного решения:

   ```bash
   git add путь/к/файлу.dart
   git commit -m "chore: resolve merge conflicts with main"
   git push
   ```

4. Merge Request автоматически обновится.

### После ревью

- Если ревьюер (Bekzhan) оставил комментарии — исправляешь, делаешь новые коммиты и пушишь в ту же ветку.
- Не делаешь `force push`, если специально не попросили.
- В мерджит `main` либо ревьюер, либо тот, кто ответственный за репозиторий (по договорённости).
